# RVN Compare — реестр решений

Главный источник требований — `docs/SPEC.md` (сжатая v0.9 + итерация 3). Здесь — решения, принятые после фиксации ТЗ, с причинами. Старый `src/lib/spec.ts` / `questions.ts` в эту рабочую область не переносятся.

## Подтверждено пользователем

1. Название — **RVN Compare Products for WooCommerce**; папка, слаг и текст-домен — `rvn-compare-products-for-woocommerce`; главный файл — `rvn-compare-products-for-woocommerce.php`.
2. Префикс кода — `rvn_compare` (PHP), `rvn-compare` (CSS/JS/шорткоды). `rvn-comrape` — опечатка.
3. Пользователь проверяет сборки на своём локальном сайте и на хостинге; к каждой сборке — точные инструкции.
4. Порядок итераций принят; разработка начата 23.09.2026 («Начинаем»).
5. Главная страница предпросмотра = текущий ответ + «Следующий шаг», обновляется каждый раунд.
6. Приоритет — прохождение автоматического и ручного аудита каталога WordPress.org без замечаний; безопасность важнее скорости разработки.

## Решения разработчика в итерации 0

| Решение | Причина |
| --- | --- |
| Пространства имён `RVN_Compare` и `RVN_Core` вместо `Revolen\RVNCompare` и `Revolen\RVN\Core` | Plugin Check выводит префикс плагина из корня пространства имён; с `Revolen` он требовал префикс `revolen` у всех хуков и дал 8 предупреждений. Варианты проверены на сканере: `RVN_Compare` + `RVN_Core` не порождают конфликтующего префикса, а один префикс `rvn_compare` во всём коде понятен и ручной проверке |
| Страницы линейки регистрируются методом `RVN_Core\Core::add_product()`, у ядра нет хуков | Хуки ядра общие для всей линейки и не могут иметь префикс конкретного плагина; прямой вызов API снимает вопрос префиксов и проще в сопровождении |
| `load_plugin_textdomain()` с `phpcs:ignore` и обоснованием | ТЗ требует встроенный перевод ru_RU. Языковые пакеты WordPress.org всё равно имеют приоритет. Перед подачей в каталог решим, оставлять ли встроенные файлы после публикации перевода на translate.wordpress.org |
| Значок «R» — текстовый символ в CSS, а не SVG | Без base64 (правило WPCS против обфускации), цвет автоматически следует цветовой схеме консоли, никаких скриптов перекраски |
| Верхний пункт `rvn` получает обработчик первой страницы линейки; дубль в подменю удаляется | Клик по «RVN» открывает первую страницу, прямой адрес `page=rvn` не пустой, стабильный id `#toplevel_page_rvn` для стилей |
| Позиция меню — середина между «Маркетингом» и следующим пунктом; запасная 58.9 | Устойчиво к изменению позиций в будущих версиях WooCommerce |
| Декларация `product_block_editor` оставлена | На WooCommerce 8.2 и 11.1 не даёт записей в журнале; плагин не добавляет полей в редактор товара |
| Сетевая активация не перебирает сайты | На больших сетях это долго; установка выполняется на каждом сайте при первом входе в консоль |
| Код `uninstall.php` внутри функции, сайты сети — порциями по 100 | Нет глобальных переменных; ограниченная память на больших сетях |
| PHPStan: `treatPhpDocTypesAsCertain: false` | Данные хуков приходят от стороннего кода; защитные проверки типов обязательны |
| Встроенные переводы включают `.l10n.php` | Быстрая загрузка переводов на WordPress 6.5+; WordPress 6.4 использует `.mo` |

## Разделение проверок: подтверждено пользователем (раунд после итерации 0)

- Устройства пользователя: только Android. iPhone/iPad и реальный Safari остаются «не проверено» в отчётах; эмуляция WebKit — единственный доступный источник данных по iOS.
- Платные темы и конструкторы не фиксируются (Avada — один из будущих сайтов, не единственный). Гарантируем базовую совместимость; универсальный путь для нестандартных карточек — шорткод `[rvn-compare-button]`. Под конкретные конструкторы подгонку не делаем.
- Локальный сайт пользователя — Local WP (есть WP-CLI как «Site Shell»); хостинг — без WP-CLI. Поэтому диагностика окружения делается **страницей «Инструменты → Диагностика RVN»** в админке (доступ только администратору): работает и в Local, и на хостинге. WP-CLI-версию той же диагностики добавляю для Local как бонус.
- Docker не нужен: пользователь подтвердил, что автопроверки полностью остаются в среде разработки.
- Тестовый сайт пользователя: простая бесплатная тема, 50 товаров, 40+ атрибутов. Рекомендуется установить два плагина: **WP Super Cache** (кэш страниц: персональная страница сравнения обязана корректно работать под полным кэшем) и **Query Monitor** (счётчик запросов и медленные запросы в отчётах). Больше ничего добавлять не нужно.

## Разделение проверок (раунд после итерации 0, ждёт подтверждения пользователя)

Предложено и обосновано: автопроверки полностью остаются в среде разработки — Docker у пользователя был бы их повторением. На сторону пользователя переходят только вещи, недоступные в песочнице: реальные устройства, платные темы и конструкторы, фактический хостинг и субъективная оценка внешнего вида. Дополнительно предлагается диагностика окружения пользователя (`wp-dev/diagnostics.php` через WP-CLI или страница в админке без него) — она проверяет реальный сайт, а не контейнер. Docker-набор (`wp-dev/docker/`) остаётся опцией на случай, если пользователю нужна независимость от среды разработки.

## Решения итерации 1 (ядро сравнения)

| Решение | Причина |
| --- | --- |
| Список гостя живёт только в браузере, сервер его не пишет | Страницы остаются кешируемыми; персональные данные не попадают в общий кэш. REST принимает список гостя для проверки и возвращает вычисленное состояние |
| Список пользователя — JSON в user_meta с `wp_slash` при записи | Требование пользователя (формат JSON) и спецификация v0.9; номер версии схемы позволяет переводить формат в будущем |
| Бизнес-исходы REST (already, limit_*, not_found) возвращаются кодом 200 с полем `status` | Клиенту проще обрабатывать единый формат состояния; 4xx остаются для нарушений протокола (nonce, валидация, throttle) |
| Адрес клиента для ограничения частоты хранится хешем | Приватность: IP не сохраняется нигде |
| В тестах REST используется форма `?rest_route=` | Работает при любых постоянных ссылках; `/wp-json/` на «простых» ссылках уходит в редирект, который неудобен для POST |
| Отрицательные ID отсеиваются приведением к целому, а не `absint` | Автотест поймал, что `absint(-1)` превращал мусор в валидный товар с ID 1 |
| Удаление данных и мультисайт уже покрывают `rvn_compare_list` и `rvn_compare_settings` | Ключи совпали со списками `uninstall.php` итерации 0 |
| Пользователь забирает папку плагина, а не ZIP | Его файловый браузер не отдаёт бинарные архивы; ZIP остаётся релизным артефактом для каталога |
| Поведение `Requires Plugins: woocommerce` принято пользователем | Ядро WordPress 6.5+ само блокирует деактивацию WooCommerce при активном расширении и активацию расширения без WooCommerce; наше уведомление остаётся страховкой для WordPress 6.4, WP-CLI и мультисайта |

## Решения итерации 2 (кнопки, счётчики, уведомления)

| Решение | Причина |
| --- | --- |
| Подключение ассетов на `wp_enqueue_scripts` с флагом необходимости | Рендер блоков вызывает вывод кнопки до формирования очереди скриптов; подключение «на месте» теряло и данные, и файлы. Флаг сохраняет экономию: файлы грузятся только на страницах с элементами сравнения |
| Данные скрипту передаются `wp_add_inline_script`, а не `wp_localize_script` | Явный inline виден в разметке и не зависит от порядка очереди; упростило поиск дефекта |
| Кнопка поверх изображения выносится из ссылки товара скриптом | Клик по кнопке внутри `<a>` открывал карточку; тема может не закрывать ссылку перед кнопкой, поэтому позиционирование и вынос делает скрипт |
| Режим кнопки для телефона задаётся атрибутом и применяется по `(hover: none)` | Точки перехода и режимы настраиваются; сенсорные устройства определяются по возможностям ввода |
| Отступы панелей и уведомлений — из настроек плюс системные безопасные зоны | Липкие шапки, нижние меню тем и полоска iPhone учитываются без правки темы |
| `viewport-fit=cover` дописывается скриптом | Свой метатег viewport WordPress не выводит, а без него браузер не сообщает размеры вырезов |
| Класс `.rvn-is-empty` скрывает нулевой счётчик | Пустой счётчик в меню выглядит как ошибка оформления |

## Решения итерации 2a (исправления по отчёту пользователя)

| Решение | Причина |
| --- | --- |
| Один обработчик на каждую позицию страницы товара, позиция проверяется внутри | Хук вызывается для всех позиций: так нет условной логики с приоритетами и легко добавить новые позиции |
| Позиции поверх изображения переносит скрипт в контейнер изображения | В классических темах слот после галереи лежит в колонке товара; позиционирование относительно колонки давало бы неверные нижние углы |
| Правила режима кнопки заданы с тем же приоритетом, что и правила состояния, и размещены после них | Иначе режим «только значок» не срабатывал в активном состоянии: появлялся лишний текст |
| Сброс кэша страниц при активации | Страницы, закэшированные до активации, отдавались без кнопок (замечание пользователя про телефон) |
| «Отменить» в уведомлении о добавлении вызывает удаление | Направление отмены теперь параметр: раньше всегда вызывалось добавление, которое возвращало «already» |
| Пауза отсчёта при наведении реализована без отдельной настройки | Небольшой объём; настройка появится вместе с вкладками дизайна |



## Решения итерации 3 (страница сравнения и таблица) — черновик кода 0.4.0

> Эти решения **выведены из кода**, который прошлый чат успел написать, но не зафиксировал в документации и не прогнал через тесты. При проверке 0.4.0 их можно уточнить; ломать без причины нельзя.

| Решение | Причина |
| --- | --- |
| Страница создаётся с shortcode `[rvn-compare-table]`, ID в `rvn_compare_page_id` | Shortcode = единая точка рендера и для автостраницы, и для ручной вставки |
| `ensure()` не трогает чужую страницу со slug `compare` | Контент пользователя священен; WordPress сам подберёт `compare-products` |
| `auto_insert_table` через `the_content` prio 8 | Админ мог стереть shortcode, страница при этом осталась «страницей сравнения» |
| `rvn_compare_page_backup` при reset | Можно вернуть ручные правки контента после случайного сброса |
| `noindex_compare_page` default on | Страница персональная (содержимое от посетителя), в индексе искать нечего |
| Таблица: HTML-оболочка без ID + `GET /table` | Кэш страниц отдаёт одну оболочку всем; персонализация только в JS |
| `table.js` рисует только через `textContent`/`el()` | XSS: названия товаров и атрибутов никогда не интерпретируются как HTML |
| Поля: core + auto attributes + explicit meta | Атрибуты магазина появляются сами; meta — только то, что явно добавил админ (scalar, no `_`) |
| `description` default off, `short_description` on | Полное описание часто длинное и шумит; short — достаточно |
| `brand` только если есть `product_brand` | На WC без брендов registry не должен содержать мёртвое поле |
| `new_attributes_enabled` default on | Новый атрибут магазина сразу в таблице, без ручного включения |
| `hide_unassigned_attributes` default on | Не показывать атрибут, которым ни один товар вкладки не обладает |
| Diff: server `smart_normalize` + client toggle | Нормализация («1 кг» vs «1kg») на сервере; UI-тогл не требует нового запроса |
| Колонки 5/3/2, breakpoints 1024/768, phone < tablet enforced | Предсказуемая сетка; sanitize не даёт перепутать breakpoints |
| `scrollbar_mode: hidden` default | Горизонтальный скролл стрелками, полоса не шумит |
| Assets table зависят от `compare.js` | Таблица переиспользует list/state/sync ядра; дублирования логики нет |
| Admin split: Page_Settings + Table_Settings | Страница и поля — разные задачи, разные capability-точки в UI |

## Рекомендации, пока не утверждённые отдельно

Экспорт и удаление персональных данных средствами WordPress, бюджеты размера скриптов (15–20 КБ кнопки и счётчик, до 40 КБ таблица), доступность WCAG 2.1 AA. Считаются инженерной нормой, но не выдаются за требования пользователя.
